Forms

How 6ixstack collects input: sections, fields, validation timing, the error summary, submit states and destructive confirmations.

Overview

Forms are how organizers get events onto 6ixstack and how anyone reaches the team: Submit an event, Edit event, Contact, Sign in and Settings. Every one of them is built from the same parts: a form card split into titled .form-sections, fields with a visible label, help and error text, a .form-actions bar with one primary button, and an error summary that appears above the card on submit.

  • Validate on submit first, then on blur for fields the person has touched, then re-validate on input once a field is invalid so the error clears as soon as it is fixed.
  • Never block typing or paste. Never clear what someone entered after an error (submit-event/error keeps every value).
  • Destructive actions in a form (delete account, cancel event) open a confirmation dialog; they are not submit buttons.

Autosave and confirmation

The mocks do not autosave; settings use one explicit Save and confirm with “Settings saved · Saved at 10:42 AM” (settings/success). If autosave is added, show the time of the last save in a polite live region and never move focus. Destructive actions sit in a .danger-zone and open a confirmation dialog that asks for the email address (delete-account).

Responsive

  • Below --layout-breakpoint-md every grid collapses to one column; .span-2 becomes a no-op.
  • On phones the long submit form keeps its action bar at the end of the form; the event detail page uses .sticky-cta instead, never the form.
  • .choice-cards stack vertically below sm and sit three across above it.
  • The settings section nav scrolls horizontally on phones and becomes a sticky column at lg.
  • Inputs stay at least --control-height-md (40px) tall; the sign-in button is .btn--lg.btn--block (48px).

Accessibility

Labels and descriptions

Every control has a visible <label for>; placeholders are examples (“https://youtube.com/live/…”), never the label. Help and error text are joined with aria-describedby="x-help x-error". Required fields use required; optional ones say “(optional)” in the label, because the mocks mark the exception, not the rule.

Errors (3.3.1, 3.3.3)

Invalid controls get aria-invalid="true". The error names the field and the fix: “End time must be after the 6:30 PM start.” On submit, focus moves to the summary (tabindex="-1", role="alert"); each summary link targets the control's id.
