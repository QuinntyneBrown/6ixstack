Feedback and loading

Which feedback answers which action — inline, toast, banner or dialog — and how 6ixstack shows loading with skeletons, spinners and progress.

WCAG 2.2 AAStatus: stableComposes toast, alert, skeleton, spinner, progress

Overview

Every action on 6ixstack gets an answer, and the answer is as small as it can be while still being noticed. This pattern decides which component answers: an inline message next to the thing that changed, a toast for a completed action somewhere else on screen, an alert or banner for a condition that persists, or a dialog only when the person must decide something. Loading follows the same principle: show the shape of what is coming (skeleton), not a blank page with a spinner.

When to use

SituationFeedbackExample from the mocks
An action completed and the result is not visible where the person isToast, auto-dismiss ≥ 8 s, optional Undo/View“Added to Google Calendar”
An action completed and the result is visibleNothing extra, or an inline statusCopy link → “Copied” inline in share dialog
A reversible bulk change (filters cleared, submission rejected)Toast with an action“Filters cleared · Showing all 14 events · Undo”
A condition that lasts until something changes (offline, unverified email)Banner or inline alert, persistent, no timer“You're offline · Showing events saved at 9:42 AM”
A request failed for the region it was loadingDanger alert in that region with Try again and an alternative“We couldn't load events … Use a calendar feed instead”
An action failed and the person can retryDanger toast with role="alert", never auto-dismisses“Couldn't copy the link · Try again”
A form was savedSuccess alert above the form with the time“Settings saved · Saved at 10:42 AM”
The person must confirm or chooseDialog“Cancel “Azure Data & AI Day GTA”?”

States

A region moves through the same states everywhere: loading (skeleton) → default → optionally empty, no results, error or partial. Actions move through idle → busy → success (toast or inline) or failed (danger alert in context, values kept).

Optimistic updates and undo

Clearing filters, marking notifications read and rejecting a submission apply immediately and offer Undo or View in the toast, rather than asking first. Deleting an account and cancelling an event are not reversible, so they confirm in a dialog instead.

Responsive

  • Toasts: bottom right, 24rem wide from --layout-breakpoint-sm; full width with --space-4 margins on phones. They never cover the sticky RSVP bar; on event detail the region moves to the top (.toast-region--top).
  • Banners span the full viewport under the site header at every width; their actions wrap below the text on phones.
  • Skeleton rows match the responsive layout of the content they stand in for, so nothing jumps when data arrives.

Accessibility

Live regions (4.1.3)

The toast region is role="status" aria-live="polite"; a danger toast adds role="alert". Inline failures that replace content use role="alert" once; persistent banners use role="status" so they are announced but do not interrupt.

Timing (2.2.1)

Success and info toasts stay at least 8 seconds and pause on hover and focus; the .toast__progress bar shows the time left. Danger toasts and anything with a Try again action never auto-dismiss.

Focus

Feedback never steals focus, except the form error summary, which receives it on submit. Busy buttons keep focus and their name; aria-busy="true" blocks repeat activation.

Motion

Toasts slide in over --duration-base and fade out on leave; skeleton shimmer runs on --duration-shimmer. Reduced motion zeroes both through the tokens; the busy spinner keeps turning because it is status, not decoration.
