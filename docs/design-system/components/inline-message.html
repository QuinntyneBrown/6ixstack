Inline message

Hints, field errors and status lines: one sentence attached to one control or object.

Overview

An inline message is one line of text tied to a single control or object: the hint under a field, the error that replaces nothing and adds to it, or a status line such as "Published · 318 going". It is the smallest feedback the system has.

  • Hint (.field__help): what to enter, shown before anything goes wrong.
  • Error (.field__error): what is wrong with this field and how to fix it.
  • Status (.inline-status): the current state of an object, with a coloured dot.

Use an alert when the message is about a whole form or region, and a toast to confirm an action. Field layout is documented on form field.

Anatomy

  1. Hint--text-body-sm, --color-fg-muted; stays visible when an error appears.
  2. Error glyph⚠ before the text, so the error is not colour alone.
  3. Error text--text-body-sm, --color-danger-fg; linked with aria-describedby.

Variants

Two or three sentences. Markdown links are fine.
Enter an email address like name@example.com.
Changing it sends a confirmation link to the new address.That doesn’t match. Type priya@gtaazure.ca exactly.
Hint only, error only, hint and error together.

  • When errors appear: after the person leaves the field (blur) or submits, never on the first keystroke. Once shown, the error updates as they type and clears as soon as the value is valid.
  • Hints stay when the error appears; the error is added below, not swapped in.

Responsive behaviour

  • Messages wrap under the control at every width; they never sit beside it, so long messages do not squeeze inputs on phones.
  • In two-column form grids (≥ 768px) each column's messages stay under their own field; rows do not align heights.
  • Status lines wrap at the middle dot; keep each segment short enough to fit 320px.

Theming

Hints read --color-fg-muted, errors --color-danger-fg, status lines --color-fg-muted with success and danger modifiers. The dot uses currentColor, so it always matches its text. The dark theme lightens the status foregrounds; no component CSS changes.

Accessibility

Role and pattern

Plain text linked to the control with aria-describedby (hint id first, then error id) and aria-invalid="true" on the control while it is in error (WCAG 3.3.1). Screen readers announce the label, the value, "invalid entry", then the hint and the error. Status lines are plain text; when one changes after a save, the change is announced through the page's live region, not by giving the line a role.

Keyboard

KeyAction
TabMessages are not focusable; focus stays on the control, and the description is read with it.

Focus

On submit, focus moves to the error summary (see alert); each summary link moves focus to its field, where the inline error is read as its description.

Labelling

Errors name the field's problem in the field's own words, so they still make sense when read from the summary. The ⚠ glyph is generated content; some screen readers read it as "warning", which is acceptable.

Motion

Messages appear without animation so they never shift content mid-read. The live dot pulses over --duration-pulse; reduced motion zeroes that token and the dot stays solid.

Touch

Not interactive. Keep links inside hints (such as "settings") at least 24px tall by giving them the line height of the text.

Content

  • Hints: what to enter or why, in a sentence: "Include the floor or room so people find you."
  • Errors: say what to do, starting with a verb: "Enter the street address for the venue." Give an example when the format is the problem: "Enter an email address like name@example.com."
  • End every hint and error with a full stop.
  • Never "Invalid input", "Required" or "Error". Never blame: "You entered…".
  • Status lines: state first, then counts, separated by " · ": "Published · 318 going · last edited Oct 28".
