Alert and banner

Alerts put a fact or a problem where it applies. Site banners do the same for the whole site.

WCAG 2.2 AAStatus: stableWAI-ARIA Alert pattern

Overview

Alerts put a fact or problem in front of people where it applies. An inline alert sits in the content it is about: a sold-out notice on an event, a failed list load, a form that did not send. A site banner runs full width above the header and is about the whole site: planned maintenance, lost connection, an account that needs verifying.

  • Use an inline alert when the message belongs to one place on the page and should stay until the situation changes.
  • Use a site banner for something every page is affected by. One at a time.
  • Use a toast for the result of an action the person just took, and an inline message for a single field.
  • Use an empty state when the whole region has nothing to show, not an alert on top of a blank list.

Anatomy

  1. Tone edge4px left border in --color-{tone}-border; 1px elsewhere.
  2. Icon20px in --color-{tone}-icon; repeats the tone so colour is never the only signal.
  3. Title--text-label; the fact, in one line.
  4. Body--text-body; what it means and what to do.
  5. Actions (optional)Underlined text links or buttons in the alert colour; at most two.
  6. Dismiss (optional)Only on information people can safely hide.

Variants

Inline alert, four tones

Tone follows consequence: info for neutral facts, success for a completed state, warning for something that needs attention but does not block, danger for something that failed or blocks.

Responsive behaviour

  • Inline alerts fill their container; the body wraps, and actions wrap onto a new line below 360px.
  • Site banners centre their content up to --layout-container-max; below --layout-breakpoint-md (768px) title and body stack and the banner text aligns left.
  • Site banners scroll away with the page; they are not sticky, so they never cover the focused element.
  • On event detail, the event alert sits above "About this event" at every width, never in the sidebar, so phones see it before the description.

Theming

Each tone sets four component tokens, --alert-bg, --alert-fg, --alert-border and --alert-icon, from the status tokens --color-{tone}-bg|fg|border|icon. The dark theme swaps the status tokens to deep tints with light text, so the alert CSS does not change.

/* A neutral announcement banner without a status meaning */
.site-banner--neutral { --alert-bg: var(--color-bg-surface-sunken); --alert-fg: var(--color-fg-default); --alert-border: var(--color-border-default); --alert-icon: var(--color-fg-muted); }

Accessibility

Role and pattern

Follows the WAI-ARIA Alert pattern only when content appears after the page has loaded and matters now: a failed load, a failed submit, a lost connection. Those get role="alert". Alerts present at page load (sold out, start time changed, maintenance) have no role; they are read in document order like any other content. Never add role="alert" to more than one element per change.

Keyboard

KeyAction
TabMoves to each link or button inside the alert, then the dismiss button.
Enter / SpaceActivates an action, or dismisses.
EscNo effect; alerts are not overlays.

Focus

An alert never takes focus, with one exception: the error summary gets tabindex="-1" and receives focus on submit, so keyboard and screen-reader users land on the list of problems (WCAG 3.3.1). After dismissal, focus moves to the next focusable element in the content, not to the top of the page.

Labelling

The title is the first thing announced; keep the fact in it. Dismiss is labelled "Dismiss". Links say where they go ("Add the address"), never "click here".

Borders are decorative; the tinted background, icon and title carry the meaning.

Motion

Alerts do not animate in. A dismissed banner collapses over --duration-base; with reduced motion it disappears at once.

Touch

The dismiss button is 24px (--target-min) square, set into the corner so it does not crowd the actions. Text actions sit 12px apart.

Content

  • Title: the fact, not the category. "Sold out", "Start time changed to 9:30 AM", "We couldn’t load events". Never "Warning" or "Error".
  • Body: what it means and what to do, in one or two sentences. Say what is still true ("Your filters are kept"; "the livestream is still free").
  • Load errors use "We couldn’t …", say whose side the problem is on, and offer Try again plus an alternative.
  • Error summary title counts the problems: "Fix 3 things before you continue". Each item is the field's own error message.
  • Banners give dates and times in Toronto time with the zone: "Sunday, Nov 8, 2–4 AM ET".
  • Use curly apostrophes (’) consistently.
